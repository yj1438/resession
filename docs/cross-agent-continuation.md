# Claude Code / Codex 双向接续调研与方案

> 调研日期：2026-10-10。
> 状态：设计提案，未实施跨 Agent 功能，未修改或导入任何真实会话。
> 本机核对：Codex CLI 0.157.1、Claude Code 2.1.258；官方在线文档可能覆盖更高版本。
> 评审补充：2026-10-10，已吸收只读架构评审；投递、绑定与恢复机制仍须通过阶段 0 实测，不视为已实现能力。
> 本文中的“Claude”指 Claude Code，“Codex”指本地 Codex CLI/可被其访问的会话，不包含普通 ChatGPT 聊天或 Claude 网页聊天。

## 1. 结论与产品边界

目标可以实现为：同一个任务在 Claude 与 Codex 间切换，首次进入另一 Agent 时创建独立原生会话，之后可以恢复该 Agent 已有关联会话并补入新增上下文。

建议以“跨 Agent 接续”为产品语义。一个任务可以关联 `claude:A` 和 `codex:B`，但它们不会变成同一个原生 ID，也不要求两份原生历史始终逐条相同。

建议第一版同步任务背景、已确认决定、最近对话与新增工作结果；原生目录、工具调用格式、内部状态和账号配置保持独立。官方导入可作为单向增强能力，不能替代双向接续协议。

不将以下目标纳入第一版：

- 改写双方私有 JSONL，使另一 CLI 把外部历史当作自己的原生历史；
- 同一份工作树上两个 Agent 自动并行修改再自动合并；
- 在来源会话生成中逐 token 同步到另一边；
- 自动同步账号、权限、模型、MCP、hooks、系统提示或全局配置；
- 跨机器、云端环境和普通网页聊天迁移。

## 2. 调研事实与证据级别

### 2.1 官方文档描述的能力

Claude Code 将会话保存在 `~/.claude/projects/`，原生 resume 延续原 ID，fork 创建新 ID。会话历史与当前磁盘文件是两回事；切 Git 分支不会同步改变对话历史。见 [Claude Code 工作机制](https://code.claude.com/docs/en/how-claude-code-works)。

Codex 官方现在提供 `/import`，可从 Claude Code 或 Cursor 导入近期会话和其他支持的设置。CLI 文档给出的范围是近 30 天最多 50 条聊天，且有运行中任务、远端会话、本地 daemon 连接等限制；桌面端有自动更新导入内容的选项。文档未保证反向写回 Claude、逐条无损或双向冲突合并。见 [官方导入说明](https://learn.chatgpt.com/docs/import)。

Claude 也有 `claude import`，但其官方说明及本机 help 描述的是导入其他编码 Agent 的**配置**，不能据此认定能反向导入 Codex 会话历史。见 [Claude CLI reference](https://code.claude.com/docs/en/cli-reference)。

Codex 提供原生 resume/fork 和结构化 App Server。后者可返回 thread ID、读取历史、发起 turn、注入模型可见 items；这些能力允许我们探索更准确的 ID 绑定与上下文交接，但不构成 Claude↔Codex 的统一会话标准。见 [CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli)、[App Server](https://learn.chatgpt.com/docs/app-server)。

### 2.2 本机协议观测，不当作稳定保证

本次仅运行 help/version，并在临时目录生成 Codex JSON Schema，没有启动模型任务：

- `codex resume` 接受 `[SESSION_ID] [PROMPT]`；新建 `codex` 接受初始 prompt。
- `codex fork` 提供原生交互会话分支入口；不能据此推断 ReSession 已能追踪运行中 ID 切换。
- Claude 支持初始 prompt、`--resume`、`--fork-session`、`--session-id <UUID>`。
- Claude 的 `--input-format stream-json` 属于 print 模式，不能直接当作原生交互 TUI 的历史导入入口。
- Codex Schema 中有 `ExternalAgentConfigImportParams`，可描述 `SESSIONS` 迁移项，以及 `ThreadInjectItemsParams`。
- Codex `ThreadResumeParams.history` 明确标为不稳定、供 Codex Cloud 使用且要求不要使用；不能选它作实现捷径。
- 本机还存在 `codex queue`，但运行中投递的时机、daemon 与重试语义仍需单独验证，不应成为两端通用假设。

这些观测需要以实际启动的二进制版本为单位做能力探测。独立 CLI 与桌面 App 内置 CLI 可能不是同一版本。

### 2.3 ReSession 当前实现的限制

项目已能分别读取两边转录并构造原生 resume 命令，统一 IR 能复用为导出基础。但是：

- Claude `uuid/parentUuid` 等原生事件关联没有进入现有 IR；
- Codex 多 rollout 分段按本地 Provider 合并，不能仅凭一个文件名定位完整历史；
- 两边工具输入/结果都被压缩为最多约 200 字符的 brief；
- 图片、加密推理、某些未知事件没有完整表达；
- Codex 的环境注入文本可能表现为 user message，不能把所有 user 文本直接当成人类需求；
- 现有 `eventIndex` 是回放位置，不适合作长期同步游标；
- 当前原生恢复与新建没有给任务链提供明确的投递回执和目标会话绑定。

因此，不能把当前 IR 导出称为“全量无损迁移”。详见 [数据格式笔记](data-formats.md) 和 `crates/session-core/src/providers/*/parse.rs`。

### 2.4 评审后新增的版本与平台边界

- Claude 官方在线文档描述：对运行中的后台会话 resume 可转为 attach，但这一行为从 **2.1.285** 起变化，不能套用到本机 **2.1.258**。文档中关于等待用户回答、特殊前缀 prompt 不转发的限制，也要连同版本和后台会话前提核对，不是所有新建/恢复 prompt 的统一规则。首版不依赖运行中 attach/转发。见 [Claude 会话管理](https://code.claude.com/docs/en/sessions)。
- App Server 当前文档将 `historyMode: "paginated"` 的新建列为尚不支持，返回 `-32601`；可列出部分摘要不代表能完整读取或恢复该类历史。若采用 App Server，先验证目标版本的受支持历史模式和 CLI 互通；遇到不支持明确停止，不回退到私有历史参数。API 历史分页与磁盘 rollout 的 `history_base` 分段不是同一机制。见 [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。
- Windows 不能统一按“32K argv”计算：当前 `.cmd`/`.bat` 包装经过 `cmd.exe`，其命令行限制为 **8,191 字符**，路径、包装参数、转义和展开也占空间。原生 `.exe` 的启动路径须另测；不能以“多 KB 都不能传入”代替实际长度核算。见 [微软命令行限制说明](https://learn.microsoft.com/en-us/troubleshoot/windows-client/shell-experience/command-line-string-limitation)。

## 3. 为什么不能直接交换全局目录里的会话文件

| 层面 | Claude Code | Codex | 跨平台接续的处理 |
|---|---|---|---|
| 存储与定位 | 项目目录下的会话 JSONL；受配置与版本影响 | `$CODEX_HOME` 下的 rollout、索引及其他状态；默认 `~/.codex` | 用 Provider 读，不硬编码目录或搬文件 |
| 会话身份 | 原生 session ID，可能有分支/父消息关系 | thread/session 身份、分段与 fork 信息 | 统一使用 `provider + native ID + 本机环境` |
| 消息/工具结构 | user/assistant、tool_use/tool_result 等 | response_item、function/custom tool call 等 | 工具结果按历史证据交接，不伪造目标工具调用 |
| 压缩与历史 | compact/分支影响可见历史与语义 | compaction/rollout/历史模式也可能演化 | 游标须带来源版本与稳定性校验 |
| 项目环境 | 当前目录、CLAUDE.md、原生设置 | 当前目录、AGENTS.md、原生设置 | 使用目标自己的配置，核对真实工作树 |
| 运行中状态 | 等待输入、执行工具、后台 Agent 等 | turn、工具、daemon 等 | 第一版只在稳定边界切换，保持同工作树串行写入 |

原生 resume 恢复的不只是聊天文字。Claude 文档还描述了已保存的模型、Agent、权限等状态，部分启动选项又必须重新提供；中断工具也不等于能重新执行到同一状态。见 [Claude 会话管理](https://code.claude.com/docs/en/sessions)。

两个 Agent 即使面对相同代码，也可能有不同的工具、项目规则、沙箱和上下文窗口。直接改几处 JSON 字段不可能保证这些语义一致。

Claude 官方还明确指出 JSONL 是内部格式，版本更新可能使直接解析脚本失效。只读适配器已经需要兼容维护；自行写入原生格式会进一步承担索引和运行时一致性责任。见 [原生数据接口与存储说明](https://code.claude.com/docs/en/sessions#export-and-locate-session-data)。

## 4. 技术路线比较

| 路线 | 优点 | 代价与限制 | 建议 |
|---|---|---|---|
| 自行转换并写原生 JSONL | 表面上像完整原生历史 | 私有格式、工具配对、签名/压缩/分支/索引一致性；版本升级难维护 | 不作主路径 |
| 官方 Claude→Codex 导入 | 可由目标官方程序处理支持的历史 | 单向、版本和范围限制；导入配置与会话须严格区分；重导入与 ID 映射未验证 | 作为可选增强，先隔离试验 |
| 交接内容作为新用户输入 | 两端都能保留原生 CLI；双向一致；不改原始历史 | 不是逐条原生迁移；需要摘要、增量与关联元数据 | 推荐主路径 |
| 全面接入双方 SDK/结构化服务 | ID、turn、回执可更准确 | 两端协议不对称；会改变“薄壳+原生终端”的产品架构 | 分阶段引入局部能力 |

第一版可保留原生 TUI，局部用结构化能力解决 ID 绑定。不能为方便同步就把 ReSession 改成两套 Agent 客户端。

## 5. 核心模型：任务链、原生会话、交接记录

```mermaid
flowchart LR
    A[Claude 原生会话 A] --> H1[交接 H1：首次上下文]
    H1 --> B[Codex 原生会话 B]
    B --> H2[交接 H2：B 的新增结果]
    H2 --> R[原生 resume Claude A]
    R --> H3[交接 H3：A 的新增结果]
    H3 --> S[原生 resume Codex B]
```

ReSession 保存一条任务链，关联两个或更多原生会话。首次切换创建目标会话；后续默认恢复该任务链里明确关联的目标 ID。用户也可选择“在目标 Agent 中新开分支”，这会产生新的节点，而不是悄悄替换原映射。

同一项目里可以有多个任务链；不能以 cwd、标题、修改时间或“最新会话”自动认定哪两个会话是一对。

建议元数据最小集合：

| 对象 | 关键字段 |
|---|---|
| 任务链 | chainId、标题、项目/工作树身份、会话节点、当前接续节点 |
| 会话节点 | nodeId、provider、nativeId、环境标识、来源节点、可用状态 |
| 交接记录 | transferId、sourceNode、targetNode、来源快照版本、选择/省略范围、正文与附件 hash、投递通道、尝试记录、状态、回执 |
| 回执 | 目标 nativeId、原生输入定位、校验规则版本、实际输入 hash、证据来源及时间；人工确认与原生核验分开 |
| 投递覆盖账本 | 按目标、来源 revision 和内容形态记录已投递范围；区分原文、人工摘要、附件引用，不以单个最大下标跨过未投递内容 |

存储建议：`~/.resession/continuations/<chainId>/` 下保存 `chain.json` 和按 transferId 隔离的交接文件。交接正文创建后不可变；重试复用同一正文和 ID。

原生会话仍是聊天事实源。此目录只存关系和交接快照，不把所有原生历史复制成另一套可独立编辑的聊天数据库，也不塞进日常 settings.json。

独立交接账本必须保留。原生 marker 用于核验和恢复，但会随 fork 被复制，也可能因清理、重写或历史可见范围变化而无法找到；它不是唯一的事务日志。“当前找不到 marker”不等于“从未投递”。本地记录也不能单独证明目标已收到，两类证据应相互校验。

交接文件含用户选择的历史资料，默认仅本机保存，不上传、不进入项目 Git；按系统能力限制文件访问。只冻结本次选中内容，不复制凭证或全局配置。正文一旦尝试投递便不再编辑；修改预览内容需生成新的 transferId。

## 6. 用户流程与双向 resume

### 6.1 第一次 Claude A → Codex B

1. 选择 Claude 会话 A，点击“用 Codex 继续”。
2. 核对原项目目录及当前 Git 工作树，选择交接范围与接下来要做的事。
3. 创建来源一致性快照，生成可编辑预览；明确标注省略的内容。
4. 原子保存交接记录，再通过 Codex 自己的启动入口创建 B。
5. 准确取得 B 的原生 ID，核验实际交接输入已保存；附件的引用和读取证据另列，不能把路径入库显示成全文已读。
6. 记录 A→B 关联与已投递覆盖范围，后续 B 由 Codex 自己保存和原生 resume。目标 ID 或回执不明确时进入待核对，不猜测绑定。

### 6.2 Codex B 做完以后切回 Claude A

1. 明确选中“回到 Claude A”，而不是 `--continue` 查找最近会话。
2. 取 B 在上次投递后新增的内容；交接中已有的 A 历史不再嵌套回来。
3. 检查 A 是否也在外部发生新增，预览两边新增内容，避免自动覆盖判断。
4. 通过 `claude --resume <A-id>` 恢复 A，将 B 的增量作为新的用户交接输入。
5. A 保存这条输入后，记录 B→A 回执；只更新实际投递内容的覆盖账本，附件未读或省略内容仍明确显示。

之后 A→B 同理：恢复 B，补入 A 的新进展。没有新增内容时直接原生恢复，不再制造一次交接。

目标会话丢失或被删除时，显示原因，允许用户明确创建新目标节点；不能自动绑定一个相同标题的陌生会话。

## 7. 上下文内容与真实性

### 7.1 内容分层

交接分三层：

- **核心交接**：任务目标、已确认约束/决定、已完成事项、未完成问题、下一步；用户可编辑。
- **对话增量**：按原始顺序附最近或指定范围的 user/assistant 消息，标明来源 Agent 与事件范围。
- **证据附件**：选中的工具输出、文件路径、测试结果、diff 信息和完整历史摘录；标明截断与缺失。

不能仅凭本地字符串算法把聊天生成“语义摘要”。第一版可以用用户填写的交接说明加确定性对话摘录；AI 自动摘要必须作为显式可选步骤，说明额外模型调用、费用和内容范围，并保存摘要来源。

历史正文应作为历史资料引用；不要将旧会话里的系统说明、工具回显、终端指令直接提升成目标的新系统规则。工具结果是“过去执行过什么”的证据，不是要目标继续完成的真实 tool_call。目标必须检查当前文件与测试状态后再决定行动。

隐藏推理、加密内容、运行中工具、进程状态、checkpoint、会话权限不承诺迁移。图片/附件第一版可明确列出引用与缺失，不静默假装已搬过去。

单有一个文件路径不等于目标已经读取全部历史。核心信息应在目标实际收到的输入中；扩展附件须验证目标的读取权限，遇到限制走目标原生授权，不能自动放开整个主目录。

### 7.2 首版投递协议：短核心内联，长证据冻结

首版建议采用下面的混合协议，而不是“全文 argv”和“仅发一个路径”二选一。具体适配器只有阶段 0 通过后才可声明支持：

1. **实际输入**包含 ReSession 交接信封、transferId、简短核心说明，以及明确的下一步；固定信封前缀避免用户正文意外变成 `/` 或 `!` 命令。用户正文、历史摘录和目标操作指令分区，不把原历史升级为新系统权限。
2. **扩展内容**保存在不可变文件中，输入列出文件路径、hash、内容范围、大小及用途。manifest 同时冻结最终输入正文；完整输入超出通道预算时，在启动前拒绝并让用户缩减，不静默改成“路径交接”。
3. **权限核验**以目标实际运行环境为准。优先验证 ReSession 自有目录；只有目标原生支持且用户确认时，才增加特定交接目录的访问范围。不得自动修改项目规则或开放整个主目录。
4. **读取状态**逐附件记录 `referenced`（路径已投递）、`readEvidence`（可核验的读取/返回内容证据）或 `unknown`。成功的文件工具调用也要检查读取范围与截断，不能仅凭模型说“已读”证明全文进入上下文。
5. **人工兜底**可提供复制交接输入后由用户粘贴，但默认自动化失败不会偷偷切换通道。人工投递仍要绑定准确 ID，并区分原生核验回执与用户确认。

因此 UI 应分别显示“交接输入已保存”“附件引用已送达/读取待确认”“任务已完成”，不提供一个笼统的“全部同步成功”。同一附件已引用但未读时可提示目标继续读取，不重发已经入库的整份交接。

### 7.3 上下文预算与费用

以下是首版试验的预览默认值，不是 CLI 或模型能力保证；阶段 0 根据实际二进制、转义和上下文限制调整：

| 内容 | 建议默认预算 | 超限处理 |
|---|---|---|
| 内联核心说明 | 不超过 2,000 个 Unicode 字符且不超过 8 KiB UTF-8；完整输入还须通过通道长度检查 | 用户缩减；不可省略的约束放不下则停止投递 |
| 确定性对话摘录 | 最近 6 轮以内，正文合计不超过 32 KiB，作为冻结扩展内容 | 明示未包含的来源范围，用户选择更多或改写交接说明 |
| 证据附件 | 单份不超过 1 MiB，本次合计不超过 4 MiB | 选择具体片段或分次读取，不能默认要求模型吞下整份大日志 |

字符/字节预算不是 token 或费用的精确估算。除了可选 AI 摘要，每次交接、读取附件和恢复长历史都可能增加目标请求的上下文与费用；实际增长受压缩、缓存、模型和计费方式影响，不承诺随轮次固定线性增长。预览展示本次字节数、附件数、被省略范围，以及原生历史仍会参与 resume 的提示。

默认不全量回灌、不自动付费摘要；用户交接说明加有界摘录是首版路径。预算导致的省略不能被推进游标隐藏。阶段 0 的模型实测成本另行确认，本次文档补充不执行任何模型调用。

## 8. 增量、去重与防回流

假设 H1 已把 A 的事件 1…20 交给 B；B 的历史将含 H1 的正文。回到 A 时只应交接 B 随后的真实新工作，不将 H1 内的 A1…20 再嵌套一次。

必要机制：

1. 每份交接都有不可变 transferId、内容 hash 和原始来源范围。
2. 接收后的原生 user message 带短交接标识；只在预期目标 ID、角色和来源定位都正确、实际输入与本地冻结内容一致时，才认定原生回执。不能把助手回显的 marker 或 fork 复制的旧 marker 当成本次新投递。
3. 导出时把既有交接正文引用为来源关系，避免再次展开；保留其后真正的新对话。
4. 覆盖账本按“哪个目标收到哪种形态的哪些来源内容”记录，而不是全局最后更新时间。只发送摘要不等于逐条原文已收到，只发送附件路径也不等于附件已读；未投递间隙仍保留。
5. 相同文本在不同时间出现不必然是重复；去重必须依据事件来源/范围，不能单纯对文本去重。

现有 eventIndex、mtime 都不够。新增导出模型要保留原生事件 ID（若可取得）、原始记录定位、分段信息及来源 revision。无原生 ID 时，以受校验的记录定位和稳定前缀摘要兜底，不能宣称严格 exactly-once。

compact、fork、重写或历史模式变化后，原游标可能失效。此时重新核对来源快照，并让用户确认新的交接范围；宁可提示“历史已变化”，也不能把一大段旧历史当新内容重复发送。

过去已核验的“输入保存”事实不会因 marker 后来消失自动变为未投递，但目标当前上下文是否仍包含它须另行标记。缺失、冲突或多匹配进入人工核对；不从“扫描无结果”推导安全重发，也不自动把旧分支的覆盖关系迁移到新节点。

## 9. 原生 ID 绑定与输入投递是首要技术试验

Claude 可以显式指定新会话 UUID，绑定相对直接；仍需确认目标实际写出该会话，并处理启动即失败或未登录。

本机 Codex help 未提供同构的交互新会话 `--session-id`。阶段 0 按以下优先级试验，不预先宣布任何一条可靠：

- **先试纯 CLI**：初始 prompt 携带 transferId，依据保存的原生 user 输入绑定 ID。必须同时核对本机环境、目标 Provider、冻结输入及唯一原生 ID；多个文件分段可属于同一个 ID，多个不同 ID 匹配则停下。marker 只是候选路线，不是已验证保底。
- **条件性替代**：纯 CLI 无法满足唯一绑定或持久化时，再试 App Server 创建并返回 thread ID，证明目标版本 CLI 能 resume、daemon 退出后仍可恢复、受支持历史模式与多进程行为明确。不得使用标为禁用的 `ThreadResumeParams.history`。
- **后续增强**：官方导入的原生 ID 映射放阶段 3 独立试验；返回 importId 不等于目标 thread ID。它不阻塞首版双向接续。

选择最小且实测成立的绑定路径；只有结构化接口确有必要时才引入其生命周期管理。任一路线均不得用目录最新文件、标题或进程启动成功冒充身份/保存回执。原生 CLI 继续负责交互与会话保存。

初始/恢复 prompt 应通过目标支持的参数或结构化接口提交。不能靠固定等待几秒后向 PTY 输入回车：那可能确认登录、信任或权限提示，甚至发到错误会话。目标正在运行时也不能再启动第二个 writer；第一版要求停止目标后恢复，运行中安全投递另做适配。

不把大段历史直接塞 argv。按 §7.2 投递短核心说明及附件引用，实际读取权限与可读文件位置必须先试验。Windows `.cmd` 与原生 `.exe` 分开测量完整命令行，不能只测正文或只测 32K；shell 转义、路径含空格/中文及特殊字符也是必验项。若无法用经过验证的参数通道安全传递，则停止自动投递，不把用户文本拼接进 `cmd /C` 命令字符串。

### 9.1 运行中的写目标变化

Claude `/branch` 会复制转录并把当前进程切换为写新 ID；`/resume`、`/clear` 等会话切换也可能使启动时绑定不再代表当前会话。Codex 的会话切换需单独实测，不能推定两端机制相同。外部新开 fork 与原进程内部切换必须分开处理。

- 启动绑定只证明当时的目标身份，不能永久证明该 PTY 对应哪个当前原生会话；PTY 键与新 ID 也不能默默混用。
- 切回来源或再次投递前，由 Provider 核对节点与原生会话身份。旧文件停止增长、新文件出现只是异常信号，不足以自动认定二者的父子/活动关系。
- 有可验证的原生关联证据时展示新节点，用户明确选择是否接续该分支；否则提示确认当前 ID，禁止自动追随“最新活跃会话”。旧节点和旧回执保留。
- 无法确认运行状态或身份时，要求停止目标并按明确 ID 恢复，或仅生成交接预览；不得再起第二个 writer 去试探。

## 10. 工作树与运行中切换

应比较真实工作树身份，包括仓库根、worktree 目录、当前 HEAD/分支和 dirty 状态。目录末级名称相同不是同一个项目；历史中记录的分支也不保证仍是当前分支。

同机器同工作树时，代码和文件变化已经在磁盘共享，通常不需要重复同步。ReSession 记录交接时的 Git 信息与变化概览，目标以当前磁盘内容为准。不会自动 checkout、提交、stash 或覆盖未提交文件。

第一版默认同工作树串行写入。来源正在生成/执行工具时先等待稳定边界或由用户停止；ReSession 的 busy 指示只是启发式，不能当作可靠 turn 完成回执。对不在 ReSession 管理内的 CLI，也不能承诺阻止所有外部并发修改。

读取来源时，记录选定文件集和 revision，核对读取前后长度/状态，忽略尾部未完整 JSONL 行；检测到变化就重取。这样保证交接是一份明确时刻的快照，而不是不断变化的文件引用。

不同 worktree/跨机器属于另一层问题：还需要代码与路径映射。首版只允许明确选定的本机工作树，不把会话同步包装成代码同步。

## 11. 失败、回执与幂等

### 11.1 生命周期与独立证据

| 状态 | 意义 | 后续处理 |
|---|---|---|
| prepared | 正文和来源范围已冻结 | 可预览、取消或开始投递 |
| launched | 目标进程启动 | 不能据此显示交接成功 |
| bound | 唯一绑定目标原生 ID | 继续确认保存的输入 |
| recorded | 预期目标原生历史保存了匹配的实际输入 | 只更新该输入的投递覆盖；附件读取与模型结果另列 |
| failed | 某一步明确失败，且该步骤是否已产生投递有证据 | 保留错误和部分成功；输入是否保存不明则不能按失败自动重发 |
| unknown | 崩溃/超时、回执缺失/冲突或身份不明 | 查原生证据与本地账本，保留人工处理出口，不自动重发 |
| cancelled | 用户放弃本次继续操作 | 保留已发生步骤；取消不撤销原生输入，也不证明未投递 |

这些状态描述本次交接的事实，不是不可跳过的单线步骤：恢复已有节点时 ID 可在启动前已知，回执也可能先于 UI 收到启动事件。状态应按证据归并，错误、附件状态与每次 attempt 单独保留，不因后到事件覆盖已核验的输入保存事实。

模型任务执行是否成功另外记录。已经保存交接输入却模型报错，不应把同一上下文再次重复发送。

回执须保存原生输入定位和校验方式，不只是一个 hash 字段。完整输入比较可采用适配器实测明确的换行等规范化规则，规则须版本化并保留原文；不能宽松到只匹配 marker。尚无可靠校验的目标降级为待核对，不能为了显示成功省略正文校验。

投递状态、目标绑定、附件读取证据和模型执行结果是独立维度。例如目标已保存输入、附件权限被拒绝时，保留 `recorded` 并显示附件未读，不把整个交接回滚成“未发送”。

### 11.2 未知状态的人工出口

UI 至少提供四个动作，每个动作都保留时间、原因和证据，不无限阻塞用户：

1. **重新核验**：只读取已有证据，不启动模型、不重新发送。
2. **人工确认已收到**：用户选择准确目标并确认内容；保存 `manualConfirmed`，不伪造成原生核验回执。只作为用户明确接受的去重决定，覆盖范围仍标注未经自动验证。
3. **放弃本次**：标记 cancelled；已保存输入和关联不会被删除，仍可回到原生会话继续。后来发现回执时作为补充事实展示，不自动恢复投递。
4. **明确重试**：先检查旧目标和尝试记录；有重复/费用风险的未知投递须由用户再次确认。未改内容复用 transferId 和冻结正文，增加 attemptId；改变正文则新建交接记录。

单纯用户关闭进度面板不等于取消，取消也不等于回滚。只有明确未投递或用户知情确认后才可重试；没有 exactly-once 保证时不承诺自动重试安全。

写本地元数据使用原子保存，按任务链/目标串行处理；多个 ReSession 实例须使用跨进程互斥或明确拒绝重复投递，不能只依赖单进程 mutex。ReSession 重启后依 manifest、尝试记录和原生证据恢复，不因游标尚未落盘就再次发送。若启动中断，新 Agent 产生了孤立会话也应展示给用户，不能自动删掉。以上互斥无法阻止外部 CLI 写入，外部变化仍需核对。

## 12. 对现有架构的改动

- `session-core`：增加有界的交接导出模型，保留选中片段的正文、来源定位、截断和省略说明；需要完整工具证据时从 Provider 重新读取，不复用已截断 brief 冒充原文。首版不是两套格式的全量无损导出工程。
- `SessionProvider`：声明交接能力、目标启动/原生恢复入口、原生 ID/回执发现方式。特殊格式处理仍由适配器负责。
- `src-tauri`：增加交接准备、快照与文件落地、任务链保存、投递/失败恢复服务；PTY 本身不解析 TUI、不改协议内容。
- `src`：交接预览、目标选择、现有关联会话或新分支选择、进度状态与来源跳转。
- 原生目录只读纪律保持；目标新增历史通过目标官方程序产生。本功能会扩展现有设计中的“仅恢复”范围，应在批准实施时同步更新 design/architecture。

目前仅批准补充提案，不视为已批准新的配置存储或运行协议。正式实施时应将 design.md 的自有数据边界扩展为“settings + 用户明确创建的交接关系/快照”，并说明取消、清理与保留政策；现有聊天事实源与 PTY 透明传输原则不变。

剪贴板修复与本方案无关，代码实施时应保持独立变更范围。

## 13. 分阶段交付与验收门槛

| 阶段 | 工作内容 | 必须证实的结果 |
|---|---|---|
| 0：技术试验 | 优先纯 CLI，隔离目录验证 ID、输入/附件证据、原生 resume、写目标切换和 Windows 通道；必要时才试 App Server | 两个方向的新建与恢复闭环成立，投递通道定案；记录准确版本、失败边界与未支持能力 |
| 1：单次接续 | 预览+有界摘录+用户说明+新目标节点+独立账本+取消/待核对出口 | 中文/长会话/路径异常/启动失败可处理，输入保存与附件状态分开显示 |
| 2：双向复用 | 恢复关联 A/B，覆盖账本、防回流、重试、内部切换与外部变化检查 | A→B→A→B 多轮不自动重复，省略/待核对明确可见；重启不自动重发 |
| 3：增强 | 官方导入可选适配、自动摘要、分支图、更多历史模式 | 按功能明确版本/损失说明，失败回退不会改原生来源 |

阶段 0 不过，就不把功能入口包装成完整双向同步。阶段 1 可以作为实验功能，不能提前承诺阶段 2 的回流与冲突处理。

阶段 0 建议先设 **2–3 个有效工作日的探索时间盒**，到点输出试验记录与 Go / No-Go，不为试完所有备选路线无限延期。该时间盒是研究投入上限建议，不是承诺功能完成；网络、CI 和双平台验证等待单列。若唯一绑定、投递或权限闭环仍不成立，收口为人工交接预览或暂缓，是否延长另行讨论。

撤回“阶段 0 至 2 共 2–4 周”的先验估算：阶段 0 通过后，按已选通道、解析增量、Windows/macOS 验证与本机 Rust/CI 条件估阶段 1/2。官方导入、无损转换、运行中投递及跨机器代码同步不计入首版，也不作为阶段 0 必须探索的并行路线。

### 13.1 阶段 0 最小试验与停止条件

| 试验 | 最小通过标准 | 未通过的处理 |
|---|---|---|
| Claude 新建/恢复 | 指定 UUID 的交接输入落盘；退出后按 ID resume，再投递不同 transferId 并核验 | 不显示自动交接成功，保留错误与版本记录 |
| Codex 新建/恢复 | marker 唯一绑定原生 ID；退出后 resume 能追加回执，含多 rollout 分段 | 禁止 mtime 猜测；仅有必要时评估 App Server 替代 |
| 正文与附件通道 | 两端短核心原样保存；文件权限与截断可观察；Windows `.cmd`/`.exe` 的长度和转义定案 | 缩减预算或仅人工交接，不静默丢内容/放宽权限 |
| 运行中身份变化 | 内部 branch/会话切换后不会将旧 PTY 误当原 ID；可靠证据不足时可停止并人工选 ID | 不发布自动追随分支能力 |
| 崩溃与重复 | 输入保存前后、账本更新前中断，重启不自动重发；缺 marker 和多匹配可人工取消/核对 | 不进入自动双向复用阶段 |
| 条件性 App Server | 受支持历史模式、退出持久化和 CLI resume 互通；不支持明确报错 | 不引入此路径，不使用私有 history 参数兜底 |

试验使用脱敏合成内容与独立配置目录；默认不导入真实会话。需要模型调用、登录复用或新权限时先确认具体范围与成本，不能因为用户批准写方案就执行真实 Agent 任务。试验记录至少包含平台、二进制来源/版本、启动参数形态、原生 ID、证据定位、失败方式与清理范围，不记录密钥。

## 14. 重点测试场景

- Claude→Codex、Codex→Claude，各自新建和恢复已关联会话。
- 三轮以上往返，含重复原文、嵌套交接、compact、fork、归档与删除。
- 区分外部 fork 与同一进程内部 `/branch`、`/resume`、`/clear`；旧 marker 被复制到新 ID 时不自动改绑或计为新回执。
- 两个同目录会话同时出现，禁止凭最新 mtime 误绑定。
- 目标未登录、CLI 版本不支持、权限拒绝、立即退出、来源追加半行、长消息和损坏 JSONL。
- Windows 路径带空格/中文；用户内容包含 shell 特殊字符；argv 长度边界。
- `.cmd` 与 `.exe` 分开覆盖；核心正文含 `/`、`!`、引号、换行、`&`、`%` 等，固定信封与参数通道不会解释成命令。
- 按版本验证后台运行、等待用户回答、未停止目标的行为；明确拒绝或进入待核对，不假定一定能 attach/投递。
- 附件拒绝访问、只读到局部、模型未读取、超预算和图片缺失：输入回执不被错误扩大为全文接收，省略范围可见。
- 目标进程启动后、输入已保存后、游标更新前分别模拟崩溃，验证不会自动重复发送。
- 回执缺失、正文规范化、多匹配、历史清理，以及人工确认/取消/明确重试；取消不删除原生输入，人工确认不冒充自动证据。
- 两个 ReSession 实例操作同一目标，与外部 CLI 同时追加时不误绑定、不覆盖账本。
- 目标能正确复述任务目标、待办与关键约束，并基于当前代码继续完成一项小任务。需要模型调用的实测单独执行并记录成本。
- 所有确定性 fixture 写在唯一临时目录；不写真实 `~/.claude`/`~/.codex`/`~/.resession`。

## 15. 推荐决策

建议批准的需求是：**同一任务的双向原生接续，已有目标会话优先 resume，通过明确交接输入补入上下文。**
