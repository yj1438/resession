# 性能基准

> 测量日期：2026-09-24 · 机器：Windows 11（9700X / EXPO6000）· `session-core` release 构建
> 方法：`cargo run --release --example bench`（确定性合成数据，自动清理，不触碰真实会话）

## 扫描 / 搜索 / 转录加载

| 数据集 | 文件数 | 体积 | 冷扫描 | 热扫描 | 冷搜索 | 热搜索 | 最大转录加载（20k 事件 / 5.4MB） |
|---|---|---|---|---|---|---|---|
| 100 会话 | 100 | 1.9MB | 19ms | 4ms | 22ms | 8ms | — |
| 500 会话 | 501 | 15.1MB | 91ms | 17ms | 128ms | 44ms | 21ms |
| 1000 会话 | 1001 | 24.9MB | 165ms | 37ms | 228ms | 83ms | 21ms |

- 冷 = 缓存清空后首次；热 = 缓存命中（扫描 3 次取中位数）
- 搜索为大小写不敏感全文匹配（词表约 10% 会话命中）

## 结论

1. **1000 会话热扫描 37ms、冷扫描 165ms** —— 15s 轮询的查询成本可忽略；即使把轮询调到 5s 也毫无压力
2. **全文搜索热路径 83ms @1000 会话** —— 现有"文本缓存 + 线性匹配"设计不需要索引（tantivy/SQLite 继续搁置）
3. **转录加载 21ms @ 20k 事件（5.4MB）** —— Rust 侧解析远非瓶颈
4. **虚拟滚动的决策点在前端 DOM 渲染**：20k 事件的转录 ≈ 数万 DOM 节点，WKWebView/WebView2 是否卡顿需要实机打开验证（用 `examples/bench.rs` 生成的数据投放到真实目录即可人工验证）；后端无需任何改动

## 复现

```bash
cd crates/session-core
cargo run --release --example bench
```

数据生成规则：10 个项目、会话事件数 40-120 随机、1/3 事件含工具调用、1/10 为 sidechain、
每第 10 个会话含搜索标记词；≥500 会话的数据集附加一个 20000 事件（5.4MB）的巨型会话。
